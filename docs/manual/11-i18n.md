# 11. Internationalisation

The library renders a few dozen strings of its own: tab tooltips, menu items, dialog text. It
translates none of them itself. The entire integration surface is one function.

## One function

```ts
const workspace = createWorkspace({
  formatMessage: (descriptor) => translate(descriptor),
})
```

A **message descriptor** is `{ id, defaultMessage?, values? }`. Your function receives it and
returns a string. That is the whole contract — nothing is imported, no locale is loaded, no
format is assumed.

Anywhere the library accepts a label — a panel title, a tab label, a menu item, dialog text —
it accepts either a plain string or a descriptor:

```ts
workspace.openPanel('map', 'map', { title: 'Site plan' })
workspace.openPanel('map', 'map', { title: { id: 'panel.sitePlan', defaultMessage: 'Site plan' } })
```

A plain string is used as-is and never reaches your formatter.

### With vue-i18n

```ts
import { useI18n } from 'vue-i18n'

const { t } = i18n.global
const workspace = createWorkspace({
  formatMessage: ({ id, defaultMessage, values }) =>
    i18n.global.te(id) ? t(id, values ?? {}) : (defaultMessage ?? id),
})
```

The `te` check means a key you have not translated yet falls back to the library's own English
rather than rendering the raw id.

### With a plain object

Equally supported, and often enough:

```ts
const strings: Record<string, string> = {
  'vdd.closeTab': 'Schließen',
  'vdd.minimizePanel': 'Minimieren',
}

const workspace = createWorkspace({
  formatMessage: ({ id, defaultMessage, values }) => {
    let text = strings[id] ?? defaultMessage ?? id
    for (const [k, v] of Object.entries(values ?? {})) text = text.replace(`{${k}}`, String(v))
    return text
  },
})
```

### Without one

Omit `formatMessage` and the built-in fallback uses each descriptor's `defaultMessage`,
falling back to its `id`, and interpolates `{placeholder}` values. English out of the box, no
configuration.

## Formatting from your own code

`format` is on the workspace, not a hook, so it works from a service, a store action or an
error handler:

```ts
workspace.format({ id: 'app.saved', defaultMessage: 'Saved {name}', values: { name } })
workspace.format(panel.title)       // a string or a descriptor, whichever it is
```

`formatLabel(label, formatter?)` is the same logic as a standalone export, for code that has
no workspace to hand.

## Every title is a `Label`

`Label` is `string | MessageDescriptor`, and it is the type of every title and label the
library holds: panel titles (`openPanel`, the registry's `defaultOptions`), side-panel and
modal titles, context-menu items, floating-widget titles, the unsaved-changes dialog.

The rule behind that: **anything the library stores, it resolves on every render.** So a
descriptor handed to any of them follows a locale change on its own, with nothing to
re-register and nothing to reopen — while a string you resolve yourself before handing it over
is frozen at the language that was current at the time, because the library has no way to
resolve it again.

Where the text comes from your own template — a `<VddToolbarButton title>` tooltip, your
panel's body — the choice does not arise: it re-renders with your component either way.

## Overriding the built-in strings

Every string the library renders is a descriptor with a `vdd.`-prefixed id, and any subset can
be replaced:

```ts
createWorkspace({
  messages: {
    closeTab: { id: 'app.dismiss', defaultMessage: 'Dismiss' },
    unsavedChangesTitle: { id: 'app.unsaved', defaultMessage: 'Hold on' },
  },
})
```

The object is merged, so a partial override keeps every key it did not name. Two reasons to
reach for this rather than translating in `formatMessage`: to re-point a string at your own
message id, and to change the wording without touching translations at all.

`workspace.messages` is the merged table, if you need to render one of the library's own
strings in your own UI — a custom drawer header that should say "Close" the same way the
library does.

For a compile-time guarantee that your own table covers every key:

```ts
import type { MessageKey } from 'vue-dockable-desktop'

const appMessages: Record<MessageKey, string> = { /* … TypeScript names anything missing */ }
```

`unsavedChangesMessage` carries a `{title}` placeholder, which the library fills with the name
of the panel being closed.

## Reading direction

```ts
createWorkspace({ dir: 'rtl' })
workspace.setDirection('rtl')       // at runtime; `dir` and `isRtl` are refs
```

What mirrors automatically:

- **Drop zones** — the left target becomes the right one.
- **Tab order and the overflow scroll buttons.**
- **Corner anchors** for floating windows and inner widgets.
- **Resize handles** — a widget pinned to the inline end offers the handle on the opposite
  *physical* side, which flips with direction.
- **Sidebar and toolbar edges**, via logical properties rather than mirrored values.

### Anchors are stored logically

This is the part worth knowing, because it affects saved layouts. An anchored floating window
records `top-left` / `bottom-right` and so on — but those names are **logical**: `left` means
inline-start. A layout saved in RTL and restored in LTR puts every anchored window on the
mirror-image side, which is the correct reading of "it was at the start of the line".

If you need a window pinned to a physical side regardless of direction, do not anchor it —
give it an explicit rect.

### The `dir` attribute

The library sets `dir` on its own elements, so a nested `dir` on your page is respected and
the library never assumes the document direction. `workspace.state.dir` is what it uses; keep
that in step with your app's own direction and everything follows.

## Coming from react-dockable-desktop

| rdd | vdd |
|---|---|
| `useFormatMessage()` | `workspace.format()` — works outside components |
| `formatLabel(label, fmt)` | same, still exported |
| `usePredefinedMessages()` | `workspace.messages` |
| `predefinedMessages` prop | `createWorkspace({ messages })` |
| `PredefinedMessageKey` | `MessageKey` |
| `useStyleClasses()` | `createWorkspace({ classes })` — see below |
| `useWindowManagerState().dir` | `workspace.dir` / `workspace.isRtl`, refs |

### `classes`, for a styling framework

Not strictly i18n, but the same shape of problem: reaching elements inside the library's own
markup. Six optional fields, added to the library's classes rather than replacing them:

```ts
createWorkspace({
  classes: {
    modal: 'MuiPaper-root MuiPaper-elevation8',
    modalBody: 'p-4',
    sidePanel: 'shadow-xl',
    sidePanelBody: 'overflow-y-auto p-3',
    window: 'ring-1 ring-black/10',
    windowBody: 'bg-white',
  },
})
```

The library's own `vdd-` classes stay, so this adds to them. Those classes are also stable
public names in their own right — styling `.vdd-modal-body` directly is equally supported, and
is the better choice when the styling is CSS rather than utility classes.
