## The milestone where the D2 fix pays off

The plan's gate condition for M12 is "a contribution published by a hidden panel is **not**
surfaced", and that is not really a property of this feature. A contribution is read from
`activePanelId`, so the whole thing is only as trustworthy as that one field.

rdd seeded `activePanelId` from `Object.keys(panels)[0]` on restore — insertion order, not
visibility — so after a layout restore with the second tab selected, the app shell's toolbar
showed the **hidden** panel's controls. Controls that looked functional and acted on something
the user could not see. That is divergence D2, fixed back in M3, and PC12/PC13 are what prove
the fix reaches the most visible place it matters.

Three tests state the invariant directly rather than by implication: a **minimised** panel
keeps publishing but is not surfaced (and is surfaced again on restore), and a **background
tab** likewise. The gate pins it structurally too: the active contribution is read from
`activePanelId` and nothing else, `Object.keys(state.panels)[0]` appears nowhere, and the
contribution store cannot import the workspace at all — so it is handed the active id rather
than able to work one out.

## A getter instead of a memoised object

rdd's `usePanelContribution(contribution)` took an object and asked the caller to memoise it,
and to call the hook on every render, because a fresh object literal each render meant
republishing each render. vdd takes a getter, so republishing follows the panel's own state
and nothing else — a `watch` handles it, and it is the framework's problem rather than the
caller's discipline.

That change surfaced a small ordering question the mutation check turned up. My first version
withdrew the old registration and then published the new one, which leaves a moment where the
panel has published nothing — observable in the same flush as a contribution disappearing.
Publishing first and withdrawing after is correct, and it is only safe because the store's
withdrawal is guarded: it clears a registration only if nothing newer has replaced it. That
guard was **dead code** until the ordering changed, which is exactly what the surviving
mutation told me. Both halves now have a test, and both mutations are caught.

## The i18n surface collapsed

rdd had `useFormatMessage()`, `usePredefinedMessages()` and `useStyleClasses()` — three hooks,
so none of it could be used outside a component. A message often needs resolving in a service;
a class list often needs to be decided in config. All three are fields on the workspace:

```ts
ws.format({ id: 'app.title', defaultMessage: 'Untitled' })
ws.messages.unsavedChangesTitle
ws.classes.modalBody
```

`createWorkspace({ messages })` merges over the defaults, so a partial override keeps every key
it did not name — asserted against the whole default table rather than one sample key. Every
built-in id is namespaced under `vdd.`, and the gate checks each one, so an application's own
message table cannot collide.

## `classes` — a port with a stronger test than the original

rdd's `useStyleClasses()` let a consumer attach their framework's utilities (Tailwind, MUI,
Bootstrap) to elements inside the library's own markup, which they otherwise cannot reach.
There was no vdd equivalent; it is now `createWorkspace({ classes })`, with six fields.

rdd's three tests for it asserted only that the hook returned the config it was given — which
is true of any object and cannot fail. The vdd tests assert the classes **reach the rendered
elements**, and that they are added alongside the library's own rather than replacing them.
That is the part that actually breaks: this library has already shipped four CSS hookups that
matched nothing (D9, D12), and a class nobody applies is the same defect in the other
direction.

## Two diagnostics, both actionable

The stylesheet sentinel had no vdd equivalent and is now checked on mount. Both diagnostics
exist for the same reason — the failure they describe produces a black rectangle and **no
error anywhere** — so each has to say what to do, not that something is wrong:

- Missing stylesheet → the exact `import` line to paste. The gate checks the line is in the
  message.
- Zero height → *where* the percentage-height chain breaks, named by walking up to the first
  ancestor with a real height, plus the `.vdd-fill-viewport` opt-in. The gate checks it names
  the ancestor rather than only complaining.

Both are development-only and both have a test proving it, so a production build carries
neither. `useColorScheme()` is ported as a ref that follows the `data-color-scheme` attribute,
with its observer disconnected on scope dispose — CS5 asserts that, because a leaked
MutationObserver per mount lives as long as the page.

## A new standing gate: `docs-api`

M11's own gate caught two documents still describing a model that had been replaced, which was
a narrow fix to a general problem: the manual is not compiled and not imported, so nothing in
the pipeline can tell when it promises an API the package does not have. That costs a reader
their trust in all of it.

`scripts/gates/docs-api.mjs` runs on every milestone now, and makes two checks narrow enough
to have no false positives:

1. Every `Vdd…` identifier a drafted chapter mentions is a real runtime export, read from
   `api-surface.json`. The prefix is the library's own, so there is nothing else it could be.
2. No chapter mentions a retired name outside its "Coming from react-dockable-desktop"
   table, where naming the old API is the entire point. The migration chapter is exempt by
   the same reasoning.

Outline chapters are skipped — they document nothing yet, so they have nothing to get wrong.
It reports how many drafted chapters it checked (13 of 14 files; chapter 13, the API
reference, is M13's work).

Two selftest cases prove it: renaming a component in chapter 6 to something unexported, and
dropping a retired name into chapter 9's body. `npm run gate:selftest`: **58** rules, all
non-vacuous.

Adding a standing check mid-plan is worth a word, since integrity rule 2 forbids editing the
gate runner to make a milestone pass. This makes the runner strictly stricter — M12 had to
pass it like every later milestone will — which is the opposite of the thing the rule guards
against.
