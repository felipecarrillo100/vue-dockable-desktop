## D5, measured

The plan's assertion for this milestone: every edge handle's hit area is its full intended
size, verified with `elementFromPoint`. Measured in Chrome on a free-floating widget, probing
each handle's centre and one pixel inside each of its four edges — 40 probes:

```
  n   186x8   centre/left/right/top/bottom  → handle
  ne   16x16  centre/left/right/top/bottom  → handle
  e     8x116 centre/left/right/top/bottom  → handle
  se   16x16  centre/left/right/top/bottom  → handle
  s   186x8   centre/left/right/top/bottom  → handle
  sw   16x16  centre/left/right/top/bottom  → handle
  w     8x116 centre/left/right/top/bottom  → handle
  nw   16x16  centre/left/right/top/bottom  → handle
```

Then the corner case, which is what rdd actually broke: a press on the widget's **visible**
corner, dragged 60×40, moved both edges by exactly that (220x150 → 280x190).

**The framing took a correction.** My first version of this assertion probed the extreme
diagonal pixel of the corner handle's box, and it failed — that pixel is clipped by the
widget's `border-radius` plus `overflow: hidden`. I nearly recorded a defect. It is not one:
that pixel is also outside the widget's *painted* shape, so nothing a user can see is
unreachable — the visible corner is the arc, and the whole arc lies inside the handle's
inscribed quarter-disc.

rdd's defect was different in kind, and worth restating because it is what the assertion has
to catch: its handles sat at `-4px`, so half of every one was outside the box and clipped away
— a nominal 8px edge left about 4px grabbable, and at the corner the entire visible arc was
outside the handle, so a corner drag did nothing at all. The gate now asserts the thing that
was broken (the visible corner reaches the handle and moves both edges) rather than a pixel
nobody can press, and the reasoning is written at the assertion so it cannot be re-litigated.
A selftest case puts a handle back at `-4px` and confirms the gate rejects it.

## Also measured, because jsdom cannot

**A stretched axis really does track the panel, with no JavaScript.** This is the claim behind
"stretch is two pins, not a width", and the only way to test it is to resize the panel. The
gate drags the grid divider and watches a full-width strip follow:

```
  overlay  638 -> 478      strip  622 -> 462
```

Always panel width minus the two 8px gutters. A measured width written once would have stayed
at 622.

**A docked widget stops at a toolbar, not at the panel edge.** Dragged 300px past the bottom
of the panel with a 48px bottom toolbar present: it grew from 180 to 684 and stopped with
**0px** overlap on the toolbar. rdd bounded growth by the raw container edge, so the same drag
went straight over it — the same class of defect a 5.x fix addressed for *positioning* and
never for resizing.

**A full-width strip and a corner widget on the same edge never overlap**, and whichever is
stacked second clears the other's full height plus the 8px gap.

## Nine refs became none

rdd's `PanelFloatingWindow` kept **nine** refs mirroring state — `modeRef`, `freePosRef`,
`sizeRef`, `stretchRef`, `currentAnchorRef`, `onPlacementChangeRef`, `snapArmedRef`,
`stackOffsetRef`, `dragState` — for one reason: a value captured in a pointer handler is stale
by the next move. A Vue ref read inside a handler is already current, so eight of those are
gone and only the drag's own scratch state remains. The `key`-remount trick and the
controlled/uncontrolled branch for `stretch` went with them.

**Anchor and stretch are one `v-model:placement`.** rdd had `defaultAnchor` plus
`defaultStretch` plus a controlled `stretch` plus `onPlacementChange` — four props for two
values — and its own comment explains why the callback reports them together: a single gesture
can change both, since releasing a stretched axis re-pins the anchor. One model is that
observation taken to its conclusion, and controlled/uncontrolled stops being a branch.

**`usePanelFloatingWindow()` is gone** — it was `useState(false)` plus three callbacks, which
in Vue is a `ref` the caller already has. `v-model:open` covers it, and PO6 asserts the model
in its place. Recorded in `PARITY.md` as a shape change.

**Three React contexts became one store.** rdd split this state across `PanelToolbarCtx`,
`PanelManagerCtx` and `PanelOverlayCtx` — not three concerns, but three slices carved to stop
a toolbar re-rendering whenever a widget gained focus, because a React context value is one
object. Vue tracks each ref separately, so one store gives the same isolation. PO10 and PO11
still assert it, and they pass.

## The geometry is pure

`core/panelOverlay.ts` imports no Vue, and the gate enforces that. The two things rdd got
wrong — which handles a placement offers, and where a released axis re-pins — are decisions
about two enum values and a direction flag, so they are now testable at every combination
rather than the handful a render happens to reach.

## Two bugs found

**A self-triggering effect.** Registering in a stack *reads* the stacks (to skip a no-op
write), so the `watchEffect` that did the registering depended on the state it wrote and
recursed until Vue gave up — "Maximum recursive updates exceeded", on ten tests, on the first
run. Explicit `watch` sources fix it, and the gate now rejects a `watchEffect` in this
component at all, since the same trap is one edit away.

**A weak test, inherited.** rdd's PO25 puts the taller card in the strip's *own* corner, where
"clears both buckets of my edge" and "clears only my own bucket" give the same number — so the
assertion could not tell them apart, and my faithful port inherited that. Found by mutation:
replacing `bucketsFor(anchor, stretch)` with `[anchor]` left all 59 tests green. Reversing the
two card heights makes the test discriminate (128px vs 98px), and the mutation is now caught.

I also added one test rdd's suite lacked: a **sub-threshold** header move must not undock
either. rdd covered the press and the real drag but never the 3px jitter in between, which is
the case the threshold exists for.

## Amended in 1.0.1 — the stretch assertion

The gate script changed after this record was written, so the record says so.

The stretch step asserted `strip.width ≈ overlay.width - 16` — the 8px gutter on each side — and
the playground's overlay has a `left` and a `right` panel toolbar, each 48px. A strip that
tracked its panel perfectly therefore measured 96px narrower than the assertion demanded, and
the gate reported `the strip is 286 wide in a 398 panel — it stopped tracking`.

That it was the gate and not the library was established before anything was touched: the same
failure, with the same numbers, reproduced against a stashed working tree at 1.0.0's source.
Under integrity rule 1 a wrong gate is a stop-and-ask, so it was reported and corrected only on
the maintainer's authorisation.

What it asserts now:

```
  {"step":"stretch tracks","overlay":"558 -> 398","strip":"446 -> 286",
   "delta":"overlay -160 · strip -160","band":"toolbars 48+48 + gutters 16","expectedStrip":286}
```

- the **tracking claim as a delta** — the strip's width changed by the same amount as the panel's
  — which no inset can skew, and which is the actual meaning of "two pins, not a width";
- the **absolute width against a measured band** — `overlay − toolbars − gutters` — so a change
  to the playground's toolbars cannot make this rule lie again.

Non-vacuity, empirically: releasing the strip's stretch before the panel is narrowed makes both
assertions fire (`strip 0px` against a panel delta of −160, and `240` against an expected `286`).
`scripts/gates/selftest.mjs` drives source gates only — a browser gate needs a served app — so
this rule's proof is that run rather than a selftest row.
